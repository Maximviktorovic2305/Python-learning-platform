# Полиморфизм

## Общий контракт важнее конкретного класса
Полиморфизм позволяет вызывающему коду одинаково работать с объектами, поддерживающими нужное поведение. Циклу форматирования достаточно метода `render` с понятными аргументами и результатом. Один объект может вернуть исходный текст, другой — преобразованный. Вызывающий код не обязан перечислять все реализации через `isinstance`, если различие уже выражено самим поведением.

Совпадение имени метода ещё не гарантирует совместимость. Одна реализация может возвращать строку, другая — непредусмотренный объект или требовать обязательный аргумент, которого нет в контракте. Поэтому общий интерфейс включает смысл, допустимые входы, ошибки и эффекты. Синтаксическое сходство является только начальной частью соглашения.

В Python такое взаимодействие возможно без общего базового класса. Это удобно для небольших адаптеров и тестовых подмен. При этом аннотации, протоколы или абстрактные классы могут сделать контракт заметнее для инструмента и читателя. Выбирайте способ описания по сложности взаимодействия, не добавляя иерархию там, где достаточно ясного небольшого метода.

## Поведение должно оставаться предсказуемым
Если потребитель ожидает строковый результат без изменения исходного текста, каждая реализация должна соблюдать это обещание. Реализация с тем же методом, которая незаметно очищает внешний список или печатает вместо возврата, меняет контракт. Такая ошибка может проявиться только после подстановки нового объекта, хотя старый пример продолжает работать.

Побочные эффекты тоже входят в соглашение. Сохранение в файл и формирование строки могут быть разными интерфейсами, даже если оба названы `render`. Не вынуждайте потребителя угадывать, нужно ли самостоятельно печатать результат, закрывать ресурс или ждать асинхронную операцию. Явное различие методов часто полезнее слишком общего названия.

Проверяйте реализации единым набором сценариев: обычный текст, пустой текст, специальные символы и повторный вызов. Затем добавляйте проверки специфического поведения каждой реализации. Общие контрактные тесты показывают заменяемость, а специальные — корректность конкретного преобразования. Один тест только самого цикла не доказывает обе стороны.

## Композиция и тестовые подмены
Потребитель может получать зависимость аргументом или через конструктор. Тогда выбор реализации происходит снаружи, а сам сценарий остаётся стабильным. Для теста легко передать объект с контролируемым ответом, не обращаясь к сети или диску. Это применение полиморфизма на реальной границе, а не упражнение по добавлению классов ради классов.

Тестовая подмена должна сохранять существенные свойства контракта. Если настоящий метод асинхронный или может вернуть отсутствие результата, подмена не должна всегда возвращать удобную строку и скрывать эти ветви. Иначе тест подтвердит только искусственно упрощённый мир. Для внешней системы дополнительно нужны проверки настоящего адаптера.

Если в потребителе постоянно появляются новые ветви по конкретным типам, спросите, можно ли передать ответственность соответствующему объекту. Однако не устраняйте любой `if` механически: иногда явный выбор формата в одном месте проще нескольких пустых классов. Цель — устойчивый понятный контракт, который выдерживает добавление действительно разных реализаций.
