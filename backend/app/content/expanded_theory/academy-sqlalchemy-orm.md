# SQLAlchemy ORM

## Модель связывает класс с таблицей
ORM позволяет работать с отображёнными объектами и их связями, но SQL и транзакции продолжают существовать. Класс модели описывает отображение, а экземпляр представляет состояние записи в определённом контексте. Создание объекта Python ещё не означает, что строка уже сохранена в БД. Для записи объект должен участвовать в работе Session и транзакции.

`DeclarativeBase`, `Mapped` и `mapped_column` делают описание модели согласованным с современным типизированным API. Первичный ключ важен не только для ограничения таблицы, но и для идентификации объекта в Session. Не используйте отсутствие ключа как удобное упрощение реальной ORM-модели: это меняет возможность однозначно отслеживать записи.

Учебное создание таблиц из метаданных не заменяет миграции рабочего приложения. При изменении модели нужно оценить, как обновится существующая схема и данные. Зелёный запуск на новой пустой базе не доказывает, что уже развёрнутый сайт сможет безопасно перейти на новую версию модели.

## Unit of work и состояние объектов
Session отслеживает изменения отображённых объектов и синхронизирует их с БД по правилам unit of work. `flush` отправляет подготовленные изменения в рамках текущей транзакции, но не равнозначен окончательному `commit`. После flush запросы могут видеть новые строки в том же контексте, хотя откат ещё способен отменить изменения.

После commit некоторые атрибуты могут истекать по настройке Session, чтобы последующее чтение получило актуальные данные. Закрытый или отсоединённый объект не всегда может автоматически загрузить истёкшее поле. Поэтому определите, когда формируется публичный результат и какие данные должны быть загружены до завершения контекста. Не переносите живую Session через случайные слои приложения.

Одна Session не предназначена для произвольного разделения между параллельными сценариями. Её состояние и транзакция принадлежат конкретной единице работы. Общий engine и отдельные Session решают разные задачи. Это различие особенно важно в сервере, где несколько пользователей обращаются одновременно.

## Запрос и внешний результат
Современный `select` можно использовать вместе с Session для выбора модели или отдельных столбцов. `scalars` помогает получить объекты или значения первого столбца без ручной работы с `Row`. Но он не выполняет сортировку автоматически: нужный порядок задаётся в выражении. Для стабильного списка используйте осмысленный критерий, включая разрешение равенства при необходимости.

Не возвращайте наружу всю ORM-модель только ради удобства сериализации. В ней могут быть приватные поля, ленивые связи и детали инфраструктуры. Сформируйте публичный DTO с явными нужными значениями. Это уменьшает риск раскрытия данных и позволяет изменить способ хранения без изменения внешнего контракта.

Проверяйте создание, чтение отсутствующей записи, обновление, конфликт ограничения и откат. Отдельно оцените число запросов при загрузке связей: удобный доступ к атрибуту способен скрыть дополнительные обращения. Понимание SQL под ORM необходимо, чтобы корректно рассуждать о производительности и согласованности, а не только об объектном синтаксисе.
