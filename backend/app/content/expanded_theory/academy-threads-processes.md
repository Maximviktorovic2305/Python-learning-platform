# Потоки и процессы

## Разные модели памяти
Потоки одного процесса обычно разделяют память, поэтому могут обращаться к общим объектам. Это облегчает обмен, но требует защиты составных изменений. Процессы имеют отдельные адресные пространства, а обмен данными выполняется через предусмотренные механизмы. Объект в памяти родителя не становится автоматически общим изменяемым объектом всех процессов.

Для задач с ожиданием ввода-вывода потоки могут быть удобны, особенно когда библиотека предоставляет синхронный API. Для тяжёлых вычислений выбор зависит от реализации и сборки Python, поведения используемых расширений и расходов передачи данных. В обычной GIL-сборке ограничения выполнения Python-кода существенны, но не следует выдавать это за универсальное свойство всех сборок и всех нативных библиотек.

Оценивайте реальную задачу и окружение. Отправка огромного объекта в отдельный процесс может потратить много времени на сериализацию и копирование. Для короткого простого вычисления последовательный цикл иногда эффективнее пула. Измерение производительности должно идти после проверки корректности, а не заменять её.

## Executor, Future и порядок map
Executor управляет работниками и принимает функции для выполнения. `submit` возвращает Future, через который можно получить результат или увидеть ошибку. `map` предоставляет результаты в порядке соответствующих входных элементов, хотя фактическое завершение работников может идти иначе. Это удобный контракт для воспроизводимого вывода.

Исключение работника не обязательно видно в момент отправки задания: оно может проявиться при чтении результата. Поэтому нельзя считать успешный submit доказательством успешной работы. Соберите или обработайте все необходимые futures и определите реакцию на отказ. Оставленный без наблюдения результат способен скрыть ошибку сценария.

Контекстный менеджер executor управляет завершением и освобождением ресурсов. Не создавайте неограниченное число отдельных потоков для каждого входного элемента. Ограниченный пул позволяет контролировать нагрузку, но размер нужно выбирать с учётом внешней системы и ресурсов. Больше работников не означает автоматически более быстрый и надёжный процесс.

## Платформа и безопасное завершение
Запуск процессов зависит от платформы и способа старта. Точка входа и доступность функции для сериализации имеют значение; локальная вложенная функция может не подходить для передачи в process pool. Не переносите пример, случайно работающий в одном режиме, без проверки поддерживаемого API и версии Python.

Браузерный WebAssembly runtime не предоставляет те же системные возможности, что обычный Python на сервере. Поэтому задания с системными потоками и процессами выполняются предусмотренным серверным исполнителем. Успешный запуск простой арифметики в браузере не доказывает доступность concurrent.futures или multiprocessing.

Проверяйте пустой источник, ошибку одного работника, порядок результата и завершение пула. Для общего состояния используйте отдельные сценарии синхронизации, не полагаясь на случайно удачное расписание. Тесты не должны требовать конкретного порядка печати из потоков, если этот порядок не обеспечен контрактом программы.
