# Аннотации типов

## Статический контракт и исполнение
Аннотация описывает ожидаемые значения для читателя и статического анализатора. При обычном выполнении Python не превращает её автоматически в проверку аргумента. Функция с параметром `int` может получить строку, если вызывающий код передал строку, а тело не выполнило собственной проверки. Ошибка может возникнуть позже либо программа продолжит работать вопреки заявленному контракту.

Это не делает аннотации бесполезными. Анализатор способен обнаружить несовместимый вызов до запуска и связать тип возвращаемого значения со следующей операцией. Но его вывод зависит от доступного типового описания и настроек. Не заменяйте проверку внешнего JSON приведением типа, которое только успокаивает инструмент и не проверяет данные в runtime.

В учебном примере намеренное нарушение аннотации показывает границу механизма, а не рекомендуемый стиль приложения. В рабочем коде такое предупреждение нужно исправлять: уточнить реальный контракт или подготовить данные до вызова. Успешный единичный запуск не доказывает, что неправильная аннотация безопасна на всех путях.

## Коллекция, элемент и отсутствие
`list[int | None]` означает список, отдельные элементы которого могут отсутствовать по контракту. `list[int] | None` означает либо целый список чисел, либо отсутствие самого списка. Эти формы требуют разных проверок. В первой нужно обработать каждый отсутствующий элемент, во второй сначала выяснить, существует ли коллекция вообще.

Аналогично аннотация возвращаемого значения должна отражать реальный исход. Если поиск иногда не находит запись, возвращение `None` следует показать в типе и обработать у потребителя. Ложное обещание всегда существующего результата переносит ошибку в неожиданное место. Не добавляйте пустую строку вместо отсутствия только ради формального соответствия типу, если по смыслу это разные ситуации.

Имена типов коллекций описывают форму, но не диапазоны и бизнес-ограничения. `int` не означает положительный идентификатор, а `str` не означает проверенный email. Для границ внешнего ввода нужны дополнительные правила, которые выполняются во время обработки данных. Типизация и валидация дополняют друг друга на разных стадиях.

## Узкая граница вместо произвольного Any
`Any` ослабляет статическую проверку операций вокруг значения. Если использовать его на всех внешних данных и затем передавать дальше, анализатор не сможет подтвердить важные свойства приложения. Лучше локализовать неизвестный ввод на границе, проверить структуру и передать внутреннему коду подготовленное типизированное значение.

Для общего поведения полезны протоколы и понятные контракты зависимостей. Потребителю может быть нужен метод чтения строки, а не конкретный огромный клиент со всеми настройками. Статическое описание такого поведения помогает подмене в тесте и уменьшает связанность. Не нужно строить универсальную иерархию ради каждого простого вызова.

Проверяйте типы вместе с тестами поведения. Анализатор обнаруживает несовместимые формы, а тест подтверждает конкретное вычисление, ошибку и отсутствие побочного эффекта. Правильно аннотированная функция всё ещё может складывать не те величины, пропускать границу или неправильно управлять ресурсом. Поэтому зелёный отчёт типизации не является заменой проверке смысла алгоритма.
