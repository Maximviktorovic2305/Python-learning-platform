# Объектно-ориентированное программирование

## Объект связывает состояние и действия
Объект полезен, когда у сущности есть состояние и понятные операции, которые должны сохранять его правила. Кошелёк содержит баланс и поддерживает пополнение; счётчик содержит текущее значение и умеет увеличиваться. Это не требование оборачивать любую арифметику классом, а способ связать данные с устойчивыми обязанностями.

Класс задаёт поведение и способ создания экземпляров. Каждый экземпляр может иметь собственные атрибуты, хотя методы описаны в общем классе. Вызов метода передаёт конкретный объект как `self`, поэтому одно определение метода работает с разными состояниями. Сравните два объекта с одинаковыми начальными числами: совпадение значений не делает их одним объектом.

Выбирайте границу по смыслу сценария. Если объект одновременно читает терминал, управляет БД, проверяет пароль и форматирует отчёт, обязанности смешаны. Небольшой связный объект проще проверить и изменить. Не создавайте иерархию из множества классов до появления реального различия поведения, которое она должна выразить.

## Состояние экземпляра и состояние класса
Атрибут экземпляра принадлежит конкретному объекту. Атрибут класса общий для класса и участвует в поиске атрибутов экземпляра. Изменяемый список, созданный на уровне класса, способен стать неожиданно общим для всех объектов. Для независимой истории кошельков или списков задач создавайте контейнер в конструкторе каждого экземпляра.

Присваивание атрибуту экземпляра и изменение общего объекта через найденный атрибут различаются. Даже одинаковая запись обращения с точкой может вести к разным последствиям в зависимости от того, где хранится значение. При неожиданном общем состоянии проверьте место создания контейнера и то, какие имена на него указывают.

Не храните вычислимую производную величину в отдельном поле без необходимости. Если диаметр зависит от текущего радиуса, метод или свойство может вычислять его при обращении. Дублированное состояние требует синхронизации: изменение одного поля должно обновить другое на каждом возможном пути. Иногда хранение оправдано стоимостью вычисления, но это отдельное обоснованное решение.

## Правила состояния и проверяемое поведение
Метод должен выражать допустимое действие, а не только предоставлять произвольный доступ ко всем полям. Если баланс не может стать отрицательным, проверяйте это в операции изменения и не оставляйте объект в повреждённом состоянии после отказа. Сначала установите допустимость действия, затем меняйте данные. Отказ является частью контракта, который также нужно проверять.

Удобный тест создаёт объект с известным состоянием, выполняет действие и наблюдает публичный результат. Проверка только внутреннего имени поля слишком тесно связывает тест с реализацией. При этом важные эффекты, например независимость второго экземпляра, следует проверять явно: один успешный результат первого объекта не доказывает отсутствия общего состояния.

Сравните объектный вариант с обычной функцией и данными. Если функция с явными аргументами проще и нет сохраняемого состояния, она может быть лучшим решением. ООП предоставляет инструменты организации, а не универсальное правило «чем больше классов, тем лучше». Качество определяется ясностью контрактов и устойчивостью изменений.
