# Модули

## Пространство имён и граница файла
Модуль содержит собственное пространство имён. Обращение `module.value` явно показывает происхождение значения. Если в текущем модуле создать имя `value`, это не изменит автоматически одноимённый атрибут импортированного модуля. При чтении программы различайте локальную привязку и доступ через точку к другому пространству имён.

Импорт с псевдонимом создаёт удобное имя модуля, а не копию его содержимого. Импорт конкретного объекта связывает этот объект с именем текущего пространства. Последующее переприсваивание одного имени не обязано менять другое. Для ясности избегайте массового `import *`: по тексту становится трудно определить, откуда взялась функция и какое имя было скрыто.

Файл с именем стандартного модуля способен случайно перекрыть ожидаемый импорт. Например, собственный файл с общеупотребительным названием может быть найден раньше нужной библиотеки. При необычной ошибке импорта проверьте путь загруженного модуля и структуру проекта, а не только наличие пакета в списке установленных.

## Выполнение при импорте и точка входа
Первый обычный импорт выполняет верхний уровень модуля, после чего результат сохраняется для последующего использования в процессе. Поэтому соединение с сетью, запуск бесконечного цикла или чтение пользовательского ввода на верхнем уровне превращает импорт в неожиданное действие. Модуль с функциями удобнее держать безопасным для загрузки и тестирования.

Блок `if __name__ == '__main__'` отделяет запуск файла как программы от его использования как модуля. Он не запрещает исполнение любых других строк верхнего уровня, поэтому важно, какие действия действительно помещены внутрь. Создание определения функции и вызов этой функции — разные этапы, как и в обычном коде.

Не используйте повторный импорт как способ надёжно сбросить состояние модуля между тестами. Кеширование, общие ссылки и порядок загрузки делают такой подход хрупким. Лучше передавать состояние явно, создавать отдельные объекты или применять контролируемую тестовую подмену на нужной границе.

## Направление зависимостей
Модуль полезен, когда имеет связную ответственность. Разделение только по длине файла создаёт случайные зависимости: функция из одного файла постоянно требует внутреннее состояние другого. Группируйте возможности по назначению и оставляйте узкий понятный интерфейс. Получателю обычно не нужны все вспомогательные детали реализации.

Циклический импорт часто показывает, что границы выбраны неудачно. Один модуль может увидеть другой в состоянии частичной инициализации, когда нужное имя ещё не создано. Технические обходы иногда необходимы, но сначала проверьте, можно ли вынести общий контракт или изменить направление зависимости. Перенос всех импортов внутрь функций не объясняет архитектурную причину цикла.

Проверяйте модуль отдельно: можно ли импортировать его без запуска приложения, подключений и пользовательского ввода? Затем проверьте публичные функции на небольшом наборе данных. Понятное пространство имён и управляемая инициализация помогают одинаково использовать код из терминальной команды, теста и серверного сценария.
